在[《把动作放回世界：具身操作的期待与问题空间》](/blog/embodied-operation-problem-space)中，我把操作系统拆成空间构建、闪念决策和接触控制。[空间构建](/blog/embodied-operation-shared-space)讨论如何压缩观测，这一篇接着讨论：**模型如何利用丰富的上下文，迅速决定下一步动作，同时保留一定的认知能力？**

我用“闪念决策”描述这样的期待：长程目标理解、知识组织和复杂规划可以交给上层大模型；端侧仍然需要理解调度、利用记忆、判断短程因果，并在现场及时改变行动。上下文可以很长，当前这一步的输出需要很快。

最初构思这一层时，我还没有参考 Jev。现在，TypeSafe 的 System One 模型提供了一个值得借鉴的方向：把模型的理解能力用于快速、结构化的判断。它尚不是机器人方案，但让“有认知能力的瞬时决策”有了更具体的参考。[Jev 官方介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

## 一、输入：统一为 token，接住丰富而不定长的上下文

### 1. 统一输入，容纳丰富上下文

我倾向于以 token 序列作为统一的输入形式，让文本、图像、空间描述和本体状态共同构成模型的上下文。

模型需要支持灵活的任务表达：既能接收简短指令，也能接收参考图、数值目标和详细的操作说明，并结合记忆与当前观测作出判断。

我期待的上下文，至少能容纳以下内容：

<div class="my-6 max-w-full overflow-x-auto">

| 内容           | 可能的形式                                       | 对操作的作用                       |
| -------------- | ------------------------------------------------ | ---------------------------------- |
| 当前 prompt    | 目标、约束、临时修改、完成条件                   | 确定现在要完成什么                 |
| 长期记忆       | 过去的操作经验、物品使用方式、稳定的偏好与约束   | 在新任务中复用已有经验             |
| 短时操作记忆   | 上层组织的多轮状态、动作、结果、分析和 reward    | 利用已有操作记录选择下一步动作     |
| 当前世界与身体 | 压缩后的操作空间、必要的局部图像、末端与接触状态 | 判断此刻可以怎样行动               |
| 细粒度调度     | 图文说明、参考图、局部区域、数值目标、动作要求   | 接受上层大模型对具体操作方式的指导 |

</div>

这些内容不必每次齐全，也不应被固定成“一句话加几帧图像”的唯一模板。简单任务可以只有目标和当前状态，复杂任务可以带参考图、多轮历史与详细约束。**输入长度和信息组合，应当随任务变化。**

### 2. 多轮记忆作为输入上下文

多轮操作记忆由上层 agent 组织，作为 query 的一部分传给下游决策模型。每一轮可以包含：

```text
操作前：世界描述 + 本体状态
执行：采取的 action
操作后：下一时刻的世界描述 + 本体状态
补充：上层提供的分析、评价或纠正（如果有）
反馈：reward、成功或失败、人工纠正（如果有）
```

上层将多组记录与当前任务、最新观测一起传入。下游决策模型读取这些已有信息，直接快速给出下一步动作。分析与记忆整理属于上层的信息组织，闪念决策的重心是利用上下文即时选择动作。

例如拉抽屉，上层可以把此前“拉动后没有位移”“调整姿态后开始移动”等记录一起传入，下游据此选择接下来的动作。这些历史记录与图像、数值要求一样，都是大脑为小脑组织的输入。

### 3. 接受大模型的细致调度

上层大模型给下游的 query，可以远比“拿起苹果”细致。例如，它可以指定从哪一侧接近、避开哪个区域、先轻触还是直接抓握，也可以用图像标出接触点，用数值限定移动范围。

画画更能说明输入为什么需要丰富：调度可能同时包含参考图、当前画面、这一笔的局部目标，以及笔触方向和接触要求。端侧需要把这些信息用于下一段操作；参考图中的外观细节，也不能都被压成一句文字描述。

[π0.7](https://www.pi.website/blog/pi07)提供了相关参考：它把任务与子步骤语言、速度和质量等元信息、控制方式以及视觉子目标纳入条件输入。对我而言，这说明操作模型的 prompt 可以描述“怎样做”，并通过不同形式的条件接入多样的数据。

在这个构想里，长短期记忆、图像、数值和详细动作要求，都属于大脑为小脑组织的 query。端侧要保留足够的理解能力，才能接住这些调度；上层则负责检索、整理和必要的长程思考。

## 二、输出：快速给出动作，同时保留模型的认知能力

### 1. Jev 的启发在哪里

Jev 的公开接口接受状态与问题，返回选择、评分或真假判断等带类型的结果。它把输出直接交给软件使用，并将同一请求中的多个判断并行处理。[官方接口说明](https://docs.typesafe.ai/introduction)

对闪念决策的启发是：**理解复杂输入与生成很长的输出，可以分开设计。** 模型可以读取丰富背景，最后只给出当前需要执行的少量结果。这可能减少逐 token 生成的开销，同时保留上下文对判断的作用。

但 Jev 与 VLA 解决的任务不同。官方展示的 Doom 示例使用结构化文本状态，并非直接读取游戏图像；软件任务上的速度与判断能力，也不能直接推导成真实机器人中的控制效果。[Jev 发布说明](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

<div class="my-6 max-w-full overflow-x-auto">

| 比较项   | Jev 的公开定位                   | 常见 VLA 路线                      | 我期待的闪念决策                     |
| -------- | -------------------------------- | ---------------------------------- | ------------------------------------ |
| 输入     | 状态与预先定义的问题             | 视觉、语言、本体状态；部分加入历史 | 丰富、可变长度的多模态上下文         |
| 输出     | 选择、评分、真假判断等结构化结果 | 动作 token 或连续动作块            | 局部意图与短段末端目标               |
| 能力落点 | 软件中的快速判断                 | 把观测和指令落到机器人动作         | 接住大模型调度，并在现场作出短程判断 |
| 主要借鉴 | 紧凑输出、并行判断               | 物理动作学习、连续动作生成         | 结合上下文理解与及时行动             |

</div>

### 2. 输出围绕末端目标组织

我仍倾向于用关键末端执行器（EEF）的位置、姿态与时间来描述下一段动作，也可以只给某个时刻的目标点。这样做主要是为了**跨本体经验迁移，尤其是复用人类操作与 UMI 数据**：不同身体可以围绕相近的末端目标，学习各自的实现方式。

具体输出可以包含三类内容：

- **meta action**：继续、改变接近方式、重新抓握、停止或恢复。
- **局部运动目标**：手、指尖或工具作用点应当到哪里，以怎样的姿态运动。
- **必要的交互要求**：保持接触、轻握、沿约束方向运动，以及任务相关的施力目标或限制。

例如擦黑板，局部目标可以是让板擦沿指定区域移动并保持接触。决策层选择擦哪里、向哪边走，身体控制层则根据接触反馈实时调整。对灵巧手，单个手腕位姿可能不够，还需要指尖、握持形态或接触要求；这也是末端接口需要继续验证的部分。

紧凑输出不意味着把所有任务硬塞进几个固定动作类别。离散选择可以采用短输出，连续轨迹可以由动作头生成；关键是让输出承载执行所需的信息，同时避免在实时路径上生成无用的长文本。

### 3. 操作训练不能只留下动作惯性

我最担心的是，模型在某个下游任务上训练得越来越熟练，却越来越听不懂新的要求：遇到熟悉画面就重复动作，忽略临时指令，也不会利用之前的失败。

我希望保留的“智慧”很具体：能理解新的调度，依据已有上下文快速选择合适的局部动作，并在收到新的观测或纠正时及时改变行动。这种能力首先体现在对丰富输入的理解和即时响应上。

[Knowledge Insulation](https://www.pi.website/download/pi05_KI.pdf)直接研究了相关问题：连续动作适配器的训练可能影响主干的学习与语言理解，因此通过离散动作学习、通用图文联合训练和动作专家的梯度隔离，改善能力迁移。这说明“接上动作输出后，怎样保留原有知识”本身就是需要设计的训练问题。

我的倾向是把能力保留作为训练目标之一：操作数据之外，继续保留图文理解与指令跟随；操作数据内部，则加入改口、纠正、失败恢复和多轮历史。评价也应检查同一个场景里，模型能否因 query 或历史不同而改变行动，而不只看单个任务的成功率。

## 三、速度：守住约 10 Hz 的响应，再争取更大的模型

### 1. 10–30 Hz 指什么

我对闪念决策的初步期待是 **10–30 Hz**，即大约每 33–100 毫秒根据新信息更新一次局部判断。这是设计目标，最终应由任务对响应的要求决定。

这里要测的是从新观测进入系统，到新的可执行决策产生的延迟，包括输入编码、上下文处理和动作输出。一次生成一秒轨迹、再以高频播放，并不等于模型每个控制周期都重新理解了场景。

动作块仍然有价值。[RTC](https://arxiv.org/abs/2506.07339)通过异步生成与已承诺动作的衔接，让模型推理时机器人继续运动。它提供了处理延迟的参考，但不会让旧观测自动变成新观测。需要立刻响应的接触变化，应由[身体控制层](/blog/embodied-operation-contact-control)处理。

### 2. 长上下文不能每轮从头计算

长上下文和低延迟之间有直接张力。我的设想是，让变化慢的任务、参考材料和长期记忆尽量复用已有计算，近期操作保留一个持续更新的窗口；关键帧、事件与摘要则由上层异步整理。

这样，丰富上下文可以一直参与判断，但每次主要处理新增信息。缓存能节省多少、图像变化会使多少缓存失效、压缩记忆是否丢掉动作细节，都需要实际测量。可变长度也应有运行预算，不能理解成没有上限。

测速度时，我尤其关心复杂上下文和临时改口后的延迟。仅用短 prompt 测到很快，不能说明系统在真实操作历史下仍然足够及时。

### 3. 为什么考虑 13–26B

我目前愿意把 **13–26B** 作为端侧模型的候选规模。与其先追求最小模型，我更倾向于先守住约 10 Hz 的有效响应，再在算力与功耗允许的范围内扩大参数量，希望保留更好的上下文理解和局部判断能力。

我也会把 8B 放进 agent 能力的起步对照，但参数量不是能力门槛。13–26B 同样是待验证的判断：端侧是否跑得动，取决于硬件、量化精度、上下文长度、视觉编码与动作头等因素；更大是否更聪明，则要用相同任务和延迟预算比较。

这一层的认知能力，主要服务于两个方向：向上，理解大模型给出的复杂、细致调度；向下，在来不及等待长程推理时，根据现场反馈作出合理选择。接触瞬间的高频调整继续交给身体，让两个层次各自承担适合的时间尺度。
